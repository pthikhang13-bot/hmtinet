# HMTI-Net — code and derived data

Reference implementation and derived artefacts for

> **HMTI-Net: Grounded Historical Memory Traceability toward Cultural Tourism Impact Analysis of
> Anti-Japanese War Films**

## What this release is, and what it is not

It is the extraction, screening and analysis chain described in the paper, together with the
artefacts from which every reported table is rendered.

It is **not** a trained HMTI-Net. The paper is a framework and feasibility study: the ontology,
the knowledge-base resolvability gate, the prefix recurrence filter, the intensity measure and
the screening analysis were executed on a 19-film corpus; the dual-channel memory bank and the
memory-reconstruction objective are specified but untrained; and the impact regression is neither
estimated nor identifiable at this corpus size. Nothing here should be read as validating the
full architecture.

## Quick start

```
python scripts/verify.py        # recompute every headline number from the shipped artefacts
python scripts/build_tables.py  # rebuild tables/ from results/ and data/
```

Both run on a fresh clone with only the standard library plus `numpy`, and neither needs network
access or the subtitle corpus.

## Layout

```
paths.py        locates the release, the shipped artefacts and the external inputs
code/
  extract/      subtitle parsing, concept extraction, gating, recurrence, intensity
  detectors/    TF-IDF and Chinese BERT baselines, and the detector comparison
  agreement/    two-coder agreement harness for the verification subset
  outcome/      search-index harvest decoding and outcome-proxy construction
  analysis/     power analysis and the verification scripts used for the paper's numbers
data/
  track_manifest.csv      per-track byte size and SHA-256 (the tracks themselves are withheld)
  film_manifest.csv       Chinese and English titles, release years, cue counts, durations
  manifest.json           16 scored concepts, positive counts, split definition
  references.bib          the manuscript's bibliography, for the reference check
  annotation/             the 968-cue two-way coding sheets and the coding guidelines
  outcome/                the six harvested search-attention series and their summary
results/
  extraction/   per-film extraction and intensity
  screening/    456-pair contingency table and the detector comparison
  agreement/    per-concept Cohen's kappa
  detectors/    TF-IDF and BERT metrics
  stability/    bootstrap stability of the concept ranking
  references/   Crossref/DataCite/OpenLibrary verification of the bibliography
tables/         the manuscript's tables as CSV, generated by scripts/build_tables.py
scripts/
  verify.py       clean-room verification of the reported numbers
  build_tables.py regenerates tables/ from results/
```

## Reproducing the reported tables

Everything in `tables/` is rebuilt by `scripts/build_tables.py` from files that ship with the
release, so no download is needed:

| Table | Content | Built from |
|---|---|---|
| 2 | films required versus effect size | closed form, `scripts/build_tables.py` |
| 4 | corpus obtained | `results/extraction/timed_extraction_results.json` |
| 6 | per-film extraction | same |
| 7 | concept prevalence | same |
| 8 | event study | `data/outcome/summary.json` |
| 9 | agreement | `results/agreement/agreement_report.json` |
| 10 | BERT per concept | `results/detectors/bert_v2_results.json` |

Re-running the *pipeline* that produced `results/` is a different matter and needs the harvested
inputs, described below.

## Re-running the pipeline

Subtitle tracks and the raw search-index dumps are third-party material and are not redistributed.
Scripts that need them stop with a message naming the missing path. To run the pipeline, point
`HMTINET_DATA` at a directory you populate yourself:

```
export HMTINET_DATA=/path/to/hmtinet-data      # PowerShell: $env:HMTINET_DATA="<path-to-hmtinet-data>"
```

with the layout

```
$HMTINET_DATA/
  subtitles/    one directory per film, holding the .ass or .srt track
  baidu/        raw harvest dumps by batch (resweep/, final/, ready/, ...)
  work/         intermediates written by the pipeline (cues.json, annotations, checkpoints)
```

`data/track_manifest.csv` gives the byte size and SHA-256 of each of the 19 tracks that were used,
so a re-obtained file can be checked before it is used. `data/selected_tracks.json` records which
track was chosen where several candidates existed.

The typical order is `code/extract/select_tracks.py`, `code/extract/extract.py`,
`code/extract/build_training_set.py`, then whichever detector or analysis script is wanted.

## Verification

`scripts/verify.py` recomputes the corpus totals, the mean kappa, the 456-pair screening
contingency table, the event-study ratios and peak offsets, the BERT macro metrics, the power
table and the reference count, and prints a pass/fail line for each. It reads only files in this
repository.

`code/analysis/verify_refs_crossref.py` re-resolves every DOI against Crossref or DataCite and
every ISBN against OpenLibrary. It needs network access.

## Withheld material

Subtitle tracks are third-party material and are not redistributed. `data/track_manifest.csv`
identifies each of the 19 tracks actually used by its path inside the harvest, extension, byte
size and SHA-256 digest, so the same file can be verified once re-obtained.

Annotation sheets do contain short dialogue excerpts. They are included because the agreement
statistic cannot be checked without seeing which cue each label refers to; they total 968 cues out
of 24,557 and are research material, not a redistribution of the films.

## Environment

Python 3.13 was used; see `requirements.txt`. The clean-room scripts need only `numpy`.

The model components additionally need a CUDA-capable GPU and a Chinese encoder, and **neither
checkpoint is redistributed with this release**. Two different encoders appear in the paper and they
are not interchangeable:

| Role | Encoder | Executed? | Where |
|---|---|---|---|
| prototype channel of the specified framework | Chinese RoBERTa-wwm, d = 768 | no | Section 3 |
| detector comparison actually run | `bert-base-TAPE`, 109.5M parameters | yes | Section 6.5 |

The reported detector figures were produced with a local copy of `bert-base-TAPE`; set
`HMTINET_BERT_CHECKPOINT` to such a copy before training. `results/detectors/bert_v2_results.json`
records the identifier. The RoBERTa-wwm encoder belongs to the part of the framework that was
specified but not executed, so no result depends on it.
